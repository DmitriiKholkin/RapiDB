# RapiDB usage notes

Detailed behavior, safety limitations, and configuration notes. For an overview and quick start, see the [README](../README.md).

## Connections and read-only mode

For MongoDB, a non-empty **Database** field overrides the database in the connection URI. Otherwise the URI database is used; if neither specifies a database, RapiDB uses `admin`. `authSource` selects the authentication database, not the database queried by the editor. An explicit `db.getSiblingDB(...)` selects the database for that operation.

Every connection has a **read-only mode** toggle. When enabled, table edits are blocked and query execution is limited to read operations. **SQL Server (MSSQL) and Oracle exceptions:** query editor execution is blocked in read-only mode because client-side classification cannot enforce read-only execution. Oracle autonomous transactions can commit writes even inside `SET TRANSACTION READ ONLY`, and caller rollback cannot undo them. Use a database account with enforced read-only permissions (including restrictions on executable routines) and a regular connection to run queries. Table data and schema browsing remain available. This toggle is an application safeguard, not a replacement for database permissions; database-defined views, policies, and routines may have side effects even during reads.

### Editing shared connection settings

- RapiDB coordinates writes to `rapidb.connections` between current-version desktop windows that share the extension's file-backed global storage. This covers User settings (including profiles that share User settings) and Workspace settings, including `.vscode/settings.json` in a single-folder window. RapiDB does not select an individual folder in a multi-root workspace. Remote Workspace writes are coordinated only from the remote workspace extension host for settings backed by that host's filesystem, and only with peers sharing its extension storage. The extension does not edit User settings in remote windows: the public API merges local and remote values and does not identify a reliable write destination. Unsupported scopes are readable; edit them using VS Code's settings editor.
- A peer may still see an old snapshot while VS Code delivers configuration changes. RapiDB refuses writes from known stale snapshots rather than replacing the list. Reload the window and review the settings before retrying. User settings in separate profiles may legitimately have identical values; where RapiDB cannot distinguish that from stale data, it also refuses the write. Restoring an earlier value (for example toggling read-only on and off) is accepted afterwards by every window of the same settings file, including after a reload: the restored value is tied to a stable identity of that file (its canonical path for workspace settings, or for User settings a per-profile token created under the coordination lock in RapiDB's profile-scoped extension storage, so windows of one profile that start at the same time agree on it), not to the window that wrote it. A window of another VS Code profile sharing the same extension storage, or a profile that shares the default profile's settings file, is refused for that restored value until the next change to the list. The coordination is **not** a compare-and-swap against manual settings edits, Settings Sync, older extension versions, or writers using separate storage (e.g. another VS Code installation, remote server, or machine sharing a workspace file). Workspace paths must also resolve to the same canonical settings path; hard links and mounts exposing the same file under unrelated paths need separate coordination. Avoid editing the same array concurrently through those paths.
- **Lock recovery:** Each lock records its owner's process ID and host name. A lock whose owner process no longer exists on the same host is taken over automatically (exactly one contender wins; a write the crashed process may still have had in flight stays fenced, so the next write is refused as stale until the settings are reviewed). Locks of processes that are still running (including suspended ones), of reused process IDs, or from another machine are never taken over. Older coordination digests are kept in a fixed-size Bloom filter, so the coordination file stays bounded; a hand-edited value can very rarely be refused as stale because of a filter collision — change it again or reset the coordination directory as described below.
- **Recovery:** If a lock remains after a crash (for example on a shared or remote file system), or a confirmed-current snapshot is still refused after reload (for example after restoring old settings by hand or an unconfirmed save), fully quit all VS Code windows and remote extension hosts that share the affected storage before resetting coordination state. Verify or back up the connection settings first. In RapiDB's extension global storage, remove the affected coordination directory under `connection-settings-v1` (`user` for User settings; a hash directory for a workspace). This directory holds only lock and digest metadata. Never remove it while an operation might still be running. Do not delete the extension storage directory itself or change keychain entries as part of lock recovery.
- **Older DynamoDB profiles without a credential source** are classified on the next connection when that is unambiguous: Secret Storage was read successfully and holds no AWS access keys for the profile, and none are in settings. A profile with a named AWS profile then uses **AWS profile**, otherwise the **default credential chain**; the source is saved to settings so a later loss of Secret Storage cannot change it (other windows reconnect once). Saved access keys keep being used as static credentials. Profiles that remain ambiguous (for example when Secret Storage cannot be read) ask you to choose the source in Edit Connection. A Secret Storage entry that was lost before the upgrade cannot be distinguished from one that never existed.
- **Saved credentials are bound to their target.** Credentials in Secret Storage are tied to the profile's non-secret target (type, host, port, database, user, URI without credentials, AWS region/profile/endpoint, TLS and SSH settings). If these change outside Edit Connection (for example by editing `settings.json`), the saved credentials are not sent to the new target; reopen Edit Connection and enter them again. Credentials saved by earlier versions carry no binding yet: they are bound to the profile's current target the first time they are used (trust on first use, under the settings lock). If that binding cannot be written (Secret Storage unavailable, or a settings scope RapiDB cannot edit in this window) the connection proceeds as before and the binding is retried on the next use, so a target changed before the first successful binding is trusted.
- **Credentials are retained on profile removal.** Removing a connection, switching it away from Secret Storage, or repairing an ID does not delete the old entry. RapiDB cannot prove that another settings scope or process no longer references it. There is no automatic orphan cleanup; if access must be revoked, rotate or revoke the credential at its source. Removing a profile is not secure erasure.

### SSH tunneling and local trust boundary

For fixed-target SSH connections, RapiDB opens a TCP listener on `127.0.0.1` at an OS-assigned port on the **VS Code extension host** (which may be a remote machine or container). Like standard SSH local port forwarding, it relays database protocol bytes to the configured host and port through SSH. Elasticsearch Cloud ID uses in-process HTTP(S) agents instead, without a local TCP listener.

Loopback prevents direct access from other machines; it does **not** authenticate local clients. Other processes able to reach that loopback interface, potentially including other OS users, can use the forward while it is open without SSH credentials. The random port is not a secret or an access-control mechanism. Each TCP connection is forwarded separately: the tunnel does not supply RapiDB's database credentials or reuse its authenticated database session for another client.

- Require database/service authentication and least-privilege permissions, even over SSH. Do not rely solely on the bastion's source IP or passwordless/trust rules for connections from the bastion: forwarded clients share that network access. RapiDB's read-only toggle does not restrict external clients.
- Use database TLS with server identity verification where supported, especially when the database is on a different host from the SSH server; SSH encryption ends at the SSH server.
- Run the extension host in a trusted environment. If untrusted local users or processes must be isolated, use OS-enforced network isolation (for example, a separate VM), not loopback alone. RapiDB does not provide protection against a malicious process running as the same OS user. Disconnect unused connections to close their forwards.

### DynamoDB credentials and AWS account verification

DynamoDB connections save an explicit credential source: access keys, a named AWS profile, or the SDK default chain. Missing saved static keys never fall back to AWS profile or environment credentials. Older profiles without a source are migrated as described in [Editing shared connection settings](#editing-shared-connection-settings); if the source cannot be determined safely, open **Edit Connection**, choose the intended source, and save.

For recognized AWS DynamoDB endpoints, RapiDB verifies the signing credentials' AWS account and partition through regional STS and binds query tabs, history, bookmarks, and Table Viewer to the verified destination. Without SSH, the extension host must be able to reach regional STS (`sts.<region>.amazonaws.com`). With SSH, the STS request uses the same SSH session as DynamoDB (a second fixed forward to `sts.<region>.<suffix>:443`, with TLS server name, certificate check and signed `Host` for the STS hostname), so the SSH host must reach regional STS — in a private subnet, add an STS interface VPC endpoint with private DNS.

If that endpoint has no private DNS, set **STS endpoint** (`awsStsEndpoint`) in Edit Connection to its HTTPS DNS name (for example `https://vpce-….sts.<region>.vpce.amazonaws.com`). It accepts only AWS STS host names for the connection's region (regional, FIPS, dual-stack or interface VPC endpoint), without port, path, query or credentials; the request is still SigV4-signed for `sts` in the connection's region, and TLS server name, certificate check and signed `Host` use that host name (with SSH, through a forward to it on port 443). The STS endpoint is part of the verified target and of the saved-credential binding, so changing it requires reconnecting and re-entering saved secrets. Account verification cannot be turned off; environment and shared-config STS endpoint overrides are deliberately ignored.

After an account or endpoint change, reconnect and review the target before running older queries. Older saved queries without a verified binding still open as text; reopen older Table Viewers from the current connection. This check does not restrict explicitly addressed cross-account table ARNs; AWS permissions still apply.

For DynamoDB Local and custom endpoints (including AWS aliases that RapiDB cannot recognize), the binding checks endpoint, signing region and — for long-term keys — the access key ID, not the identity of the backend behind that address. Temporary credentials (with a session token) get a new access key ID on every refresh, so for them only endpoint and signing region are bound; a different account reached through the same custom endpoint with temporary credentials is not detected. RapiDB does not probe STS for these endpoints; a selected AWS credential provider may still use its usual authentication services.

## SQLite runtime

SQLite connections use the native [better-sqlite3](https://github.com/WiseLibs/better-sqlite3) module (currently 13.2.0, which bundles SQLite 3.54.1). It is not included in the extension package. When you first open a SQLite database, RapiDB checks that this computer can run it, asks for confirmation and then:

- downloads `https://registry.npmjs.org/better-sqlite3/-/better-sqlite3-13.2.0.tgz` (about 11.6 MB, 1 MB = 1,000,000 bytes), showing the progress in a notification that has a **Cancel** button. Cancelling stops the download and installs nothing; open the database again to retry. Closing a connection that is waiting for the download does not cancel it. Only HTTPS connections to `registry.npmjs.org` on the default port are used, including after redirects; npm registry, mirror and proxy settings and environment variables are ignored. VS Code's proxy settings apply.
- checks the archive size and SHA-512 integrity against values pinned in RapiDB before opening it, then extracts only the package's JavaScript files, its LICENSE and package.json, and the one prebuilt binary for your platform. Archive entries that are links, devices, outside the package, reserved Windows device names, or escape the target directory are rejected, and every extracted file must match its own pinned SHA-256 hash. No install scripts, compilers or build tools are run.
- stores the runtime in the extension's global storage under `sqlite-runtime/better-sqlite3/<version>/<platform>-<arch>-<pins>`, publishing it atomically. Concurrent VS Code windows share one download.

In released builds, RapiDB loads better-sqlite3 only from this verified runtime, never from a `node_modules` folder elsewhere on the computer. Development and test builds may use a local copy from `node_modules` instead; that fallback is not present in the published extension.

The prebuilt binaries use Node-API, so one binary per platform works with every supported VS Code version; a VS Code update does not require a new download. Supported platforms are macOS, Windows and Linux on x64 and arm64; on Linux, RapiDB selects the glibc or musl binary from the C library loaded into the extension host and refuses to guess if this cannot be determined reliably. 32-bit systems (for example Raspberry Pi OS 32-bit, `linux-armhf`) and other operating systems are not supported. SQLite requires VS Code 1.101 or later (Node-API 10).

On Linux with glibc, the prebuilt binary requires **glibc 2.34 or newer** and **libstdc++ from GCC 11 or newer** (`GLIBCXX_3.4.29`), for example RHEL, Rocky Linux, AlmaLinux or Oracle Linux 9, Ubuntu 22.04, Debian 12, Fedora 35 or newer. VS Code itself still runs on older distributions, but SQLite connections do not: RHEL, CentOS Stream, Rocky Linux, AlmaLinux and Oracle Linux 8 (glibc 2.28), Ubuntu 20.04 (glibc 2.31), Debian 10 and 11 (glibc 2.28 and 2.31) and SUSE Linux Enterprise / openSUSE Leap 15 releases with glibc 2.31 are not supported. On these systems RapiDB reports the glibc version it found before asking to download anything. If the glibc version cannot be determined, RapiDB does not download the runtime. The libstdc++ version is checked in advance only if the extension host has already loaded a libstdc++; otherwise an older libstdc++ is reported when the runtime is loaded. On musl-based Linux (for example Alpine), the `libstdc++` package must be installed (`apk add libstdc++`), as it already is for the VS Code Server.

The installed runtime is verified each time a SQLite connection opens and is used without network access. It must contain exactly the expected files and folders (no additional, missing, renamed or linked entries, compared by exact name, so a differently capitalized name also counts) and every file must match its pinned hash. Otherwise RapiDB does not load it and asks again before reinstalling; the damaged runtime is first moved aside in a single step and then deleted. If another VS Code window still has it loaded (on Windows), it cannot be moved: close SQLite connections in other windows and try again. If a file of the runtime cannot be read at the moment (for example while an antivirus scan holds it), the connection fails with a message asking you to try again, and nothing is reinstalled or deleted.

In untrusted workspaces (Restricted Mode) the runtime is not installed: the error message explains how to trust the workspace (**Workspaces: Manage Workspace Trust**). A runtime that is already installed is also used in untrusted workspaces.

Runtimes for other versions, platforms or pins, including the ABI-specific runtimes of earlier RapiDB releases, are removed from the extension storage after 30 days without use. Runtimes from RapiDB versions that did not record use are removed only once nothing in them has been modified for 30 days. A runtime is never removed while another window holds its installation lock; removal is a single rename followed by deletion, and anything left over is deleted on a later start.

To set up a computer without access to `registry.npmjs.org`, open a SQLite database once on a computer with the same operating system, architecture (and, on Linux, C library) and the same RapiDB version. Then copy the `sqlite-runtime` folder from RapiDB's global storage folder on that computer to RapiDB's global storage folder on the offline computer. The copy is used only if it contains exactly the files RapiDB installed and every file matches the pinned hashes. Copy the folder as a whole and do not add files to it (for example, `.DS_Store` files created by Finder); otherwise RapiDB treats the copy as damaged and offers to download the runtime again.

RapiDB's SQLite date, time and datetime filters use one rule for all three: an hour of 24 is the next day, so `24:MM[:SS]` means `00:MM[:SS]` of the following day (`2024-01-01 24:30` is `2024-01-02 00:30`, `2024-12-31 24:00` is `2025-01-01 00:00`). Minutes and seconds must still be at most 59, so values such as `24:60` or `25:00` never match a comparison, range or list filter. Values with an offset (`Z`, `+02:00`) are compared in UTC, also for the day of a DATE filter. Values in formats RapiDB does not parse itself (for example Julian day numbers stored as text) are normalized by SQLite's `DATETIME()` first, as before. This differs from SQLite 3.54's own date functions, which accept an hour of 24 only as exactly `24:00:00` (`DATE('2024-01-01 24:30')` and `TIME('24:30')` return NULL); queries you write yourself in the Query Editor follow SQLite. Displayed and exported values are not changed.

## PostgreSQL inheritance in Table Viewer

Browsing, filtering, Export All, and row mutations use only the selected table for classic `INHERITS`, because a primary key is local to that table. Open a child table separately to work with its rows, or use the Query Editor for a recursive query. Declaratively partitioned tables still include their partitions. If RapiDB cannot determine the table's scope from PostgreSQL catalogs, it does not fall back to reading or changing an inheritance tree. Export All does not take a transactional snapshot of concurrent changes.

## PostgreSQL Query Editor result size

In addition to the row limit, the Query Editor uses conservative size budgets of 256 KiB per value and 8 MiB across retained rows and column metadata for a script. The budgets account for decoded values and display encoding, including hex for binary data and escaped text. Each displayed set is a prefix of complete rows; after the first row that does not fit, the rest of that set is omitted, and later sets can use any budget left. The editor also caps the result message to the webview at 8 MiB of JSON. Size limits affect display, not which statements execute or commit. They do not prevent the PostgreSQL client from allocating an individual wire row, and they do not limit server-side work.

CSV and JSON exports from the Query Editor export the selected, displayed result set only. For a truncated or partial set, the editor asks for confirmation; a result withheld entirely at the transfer limit is unavailable for export. Use a smaller projection or smaller values for inspection. For a full export, use Table Viewer **Export All** where applicable or an appropriate PostgreSQL export client for an arbitrary query. Adjusting the Query Row Limit does not raise the byte limits.

## Deleting rows in the SQL Table Viewer

Delete checks the stored row version or original values from the loaded page in the DELETE itself, even when mutation preview is disabled. If a selected row no longer matches, the delete batch is rolled back; refresh and review the rows before retrying.

- PostgreSQL uses the table and physical row version; a table rewrite can also invalidate a preview. SQL Server uses a non-nullable `rowversion` where available and also checks legacy LOB columns that can change without advancing it.
- SQLite, MySQL, Oracle, and SQL Server tables without a usable `rowversion` compare digests of stored values. This detects changed values, including changes that display formatting can hide. For Oracle LOBs, the Viewer also locks the key before running the guarded DELETE so it compares current contents after a concurrent LOB writer finishes. Value comparisons cannot distinguish an identical reinsertion or a change that was reverted before the DELETE. These digests are not unique row identifiers.
- If a trustworthy snapshot is unavailable, the Viewer refuses to delete that row instead of falling back to its key. Examples include non-NULL MySQL JSON (its text representation can lose native nested types), Oracle `LONG`/`LONG RAW` and unsupported non-NULL complex types, Oracle character LOBs longer than 500 units or BLOBs longer than 2,000 bytes, and relations that cannot expose the required evidence. This does not disable updates.

## Deleting rows in NoSQL Table Viewer

- **MongoDB:** On a verified standalone or non-sharded replica set, delete checks the typed `_id` and the full document against the BSON from the grid read. Field presence and order, BSON types, and binary bytes/subtypes are compared with simple collation in the delete filter. Server `$eq` compares numbers by value, so the filter adds exact checks where that is not enough: the sign of a zero double (`$atan2`), and the exact Decimal128 representation as text (`1.0` and `1.00` differ); regular expressions compare pattern and options. Documents without exact BSON evidence are not deletable from the grid: unsupported `_id` types, NaN doubles and NaN or non-canonical Decimal128 values (payloads are not comparable), deprecated or ambiguous BSON types, and documents over 256 KiB, with more than 2,048 values, or nested more than 12 levels (each level adds several levels to the server-side expression, which must stay below MongoDB's nesting limit).
- **Redis:** On Redis 7+, the grid can observe strings up to 64 KiB and collections that pass the compact-encoding check below. Collections read page by page and all values on Redis before 7 (no `PEXPIRETIME`) cannot be deleted from the grid. An atomic script compares the exact key, Redis type, absolute expiration time, and raw string bytes or Redis `DUMP` bytes. For hashes it also compares the visible raw field/value pairs, so an expired field is detected even if the dump is unchanged. Missing or partial observations never fall back to key-only deletion. An internal encoding change can make a collection conflict even when its displayed values look unchanged.
- **DynamoDB:** Grid delete is disabled. A `DeleteItem` condition can check named attributes, but cannot check for newly added attributes, and DynamoDB supplies no general item version. Browsing and editing are unchanged.
- MongoDB and Redis compare **state**, not a unique revision: an identical replacement or a change reverted before the delete can still match. If a large page exceeds the observation budget, reduce the page size. Each selected row is checked independently; one conflict does not roll back earlier successful deletes. Refresh and review before retrying, especially after an unacknowledged write. These checks apply even with preview disabled and do not change Query Editor commands.

Redis delete previews show one guarded operation per unique key, in execution order. The batch is not atomic: Redis processes keys separately, and a conflict or failure does not roll back keys already deleted. With `rapidb.skipTableMutationPreview` enabled, the command list is omitted, but deleting multiple Redis keys still requires confirmation.

## Redis browsing

Redis keys are grouped by the prefix before `:`. **All keys** and **Unprefixed keys** are separate views; prefixed groups are shown as patterns such as `default:*` and `users:*`. Edits and deletes still address the exact stored key.

Prefix groups are literal: `*`, `?`, `[`, `]`, and `\` inside a stored prefix are escaped in the Redis scan pattern, so selecting one group cannot include a different prefix through wildcard expansion.

Redis table reads and exports deduplicate `SCAN` replies and use exact-key tie-breaks when Unicode keys have equal locale collation. A repeated cursor or more than 5,000 scan requests fails explicitly rather than presenting an incomplete result. Cancellation stops waiting and prevents further reads; commands already sent may still complete. Exports are not transactional snapshots of a concurrently changing keyspace.

- Strings up to 4 MiB can be read with `STRLEN` and byte-bounded `GETRANGE`, including on Redis before 7. If the string grows past the requested range, the grid shows a marker instead of a prefix. This path can display a value but does not provide delete evidence.
- On Redis 7+, hashes, lists, sets and sorted sets are loaded only if a read-only script verifies a supported uncompressed encoding (`listpack`, `listpackex` for hashes, or `intset` for sets), at most 1,000 entries, and at most 64 KiB of Redis backing allocation. The ACL must allow `EVAL_RO`, `OBJECT ENCODING`, `MEMORY USAGE`, and the relevant size/value reads. The check and value read are atomic. Optional delete evidence needs `EVAL_RO` and `PEXPIRETIME` plus `GET` for strings or `DUMP` for collections.
- Otherwise (Redis before 7, `EVAL_RO` denied, or a non-compact encoding such as `hashtable`, `skiplist` or `quicklist`), hashes, lists, sets and sorted sets with at most 1,000 entries are read **page by page**. Before any member is transferred, `MEMORY USAGE key SAMPLES 0` must report at most 1 MiB; it walks every element and counts allocations, which are never smaller than the member bytes. Lists with the `quicklist` encoding additionally require `CONFIG GET list-compress-depth` to return `0`, because compressed nodes make the memory estimate smaller than the data. Pages use `HSCAN`/`SSCAN`/`ZSCAN` with `COUNT 64` or `LRANGE` windows of 64 elements; the bytes of every reply are counted and the read stops once the members exceed 256 KiB or 1,000 entries, showing a `RedisValueTooLarge` marker instead of a partial value. Residual bound: the preflight and the pages are separate commands, so members added concurrently after the preflight can make one page reply larger than 1 MiB (about 64 entries — `SCAN` may return a few more from one hash bucket — each up to Redis's `proto-max-bulk-len`) before it is counted and discarded. A paged value is not an atomic snapshot (members changing during the read can be missed or mixed), so it is display data only: it never provides delete evidence and grid deletes for those rows are refused with an explanation. Sorted sets are shown in rank order (score, then member bytes).
- For streams, module values, Redis before 4 (no `MEMORY USAGE`), denied preflight commands, and reads that cannot be bounded with the available commands, the grid keeps key, type, and TTL and marks the value unavailable. Filtering or sorting by value and exports fail rather than using a placeholder as data. These limits do not change commands run in the Query Editor.
- Each Table Viewer read reserves space for in-flight values and retained value payloads within a 64 MiB budget. A driver runs up to four value commands at once across pages. This is a value budget, not a cap on `SCAN` replies, metadata, or the extension host's heap.

## Query text privacy and cleanup

- **Storage:** History and bookmarks persist SQL/query text (only outer whitespace is trimmed), connection IDs, pinned PostgreSQL database names where applicable, and timestamps in VS Code's extension `globalState`, shared across workspaces rather than stored in workspace files. This is not credential `SecretStorage`: literals, comments, and any secrets in query text are not redacted. History recording is requested before the driver executes, so failed or cancelled queries can remain; history is not a log of successful executions.
- **History:** Set `"rapidb.queryHistoryLimit": 0` in VS Code user settings to stop new history entries (default: 100, shared across connections). Lowering the limit while the extension is active trims excess entries, including clearing history when changed to 0. To explicitly clear existing history, use **Clear History** (trash icon) in the **Query History** view header and confirm **Clear**. There is no individual history-entry deletion command.
- **Bookmarks:** The history limit does not disable or clear bookmarks. Avoid **Bookmark** if you do not want to save query text. Right-click an entry in **Bookmarks** → **Delete Bookmark** to remove one, or use **Clear Bookmarks** (trash icon) in that view's header and confirm **Clear** to remove all. Clearing history does not clear bookmarks. These cleanup commands are not shown in the Command Palette.

These controls only manage history/bookmark entries, not copies elsewhere. Editor drafts, including unexecuted text, can persist separately in VS Code webview state even with history disabled; clearing history/bookmarks does not clear those drafts. Cleanup does not guarantee secure erasure from storage or backups.

## Query execution

PostgreSQL definition tabs opened from the Explorer are pinned to the selected database on that connection. The title and toolbar show the target; restoring a tab or reopening its history or bookmarks keeps the same target. If the pinned target is unavailable, execution fails instead of falling back. Open a new query to use a different connection. Regular query tabs still use the profile's default database. Older tabs and saved entries without a recorded database cannot be retroactively pinned; verify their target before running them.

For PostgreSQL, MySQL, SQL Server, and SQLite, finish explicit transactions with `COMMIT` or `ROLLBACK` in the same executed script (or `RELEASE` for an outermost SQLite `SAVEPOINT`). Unfinished transactions are not kept for a later Execute. SQL Server keeps one session across the script's `GO` batches and cleans it before another query can borrow it; cancelling or timing out a query is not proof that earlier commits were undone. After a failed or cancelled write, verify the data before retrying: earlier changes may already have committed.

Elasticsearch and DynamoDB use a single SDK request attempt, including for reads: automatic retries are disabled because a lost response or server error can follow a committed write. This also overrides `AWS_MAX_ATTEMPTS` for DynamoDB. After a failed mutation, refresh and verify the data before retrying; the first request may already have applied.

A query error counts as a finished run (Run is not blocked as an unknown outcome) only when the request provably did not take effect: Elasticsearch answered with an HTTP 4xx error other than 408, 425, 429 or 499 on its first attempt, or DynamoDB returned a client error on its first attempt — for example `ValidationException`, `ConditionalCheckFailedException`, `ResourceNotFoundException` or `AccessDeniedException`, or `TransactionCanceledException` whose reasons are only condition, validation or item-collection-size failures. A script that fails before its first request (for example malformed JSON) also counts as finished. Server errors (5xx), throttling, transaction conflicts, timeouts, connection loss and cancellation leave the outcome unknown; verify the data before running again. Elasticsearch `_bulk`, `_update_by_query`, `_delete_by_query` and `_reindex` errors are always treated as unknown because they can follow partial work.

### DynamoDB

DynamoDB native JSON uses the official AWS `AttributeValue` format: `B` and `BS` contain canonical base64 strings, never hex or raw text. Binary values (including strings such as `"0xAB"` that also resemble hex) are decoded only as base64. AttributeValue shapes and binary encoding are checked across the script before its first request; scripts are still not transactions. Legacy updates with `AttributeUpdates` are dispatched as `UpdateItem`, including when `Expected` or `ReturnValues` is present.

### Elasticsearch

Elasticsearch REST scripts validate supported endpoints and body shapes before sending the first request. DELETE requests and non-search GET requests reject JSON bodies instead of silently discarding them: `DELETE /index` deletes the entire index, not documents matching a body filter. Scripts are not transactions; server-side errors can still follow successful mutations.

Elasticsearch REST paths must start with `/` and address the current connection. Absolute URLs, fragments, backslashes, invalid Unicode, and literal or percent-encoded `.` / `..` path segments are rejected before any request in the script. Encode document ID delimiters such as `/`, `#`, and `?` as `%2F`, `%23`, and `%3F`; URL normalization must never turn a document operation into an index operation.

Table Viewer pages share one Elasticsearch point-in-time snapshot, so page order stays consistent and external changes are not shown until a new snapshot. Refresh, changing filters, sort or page size, and verifying a Viewer write start a new snapshot. If the snapshot expires (45 seconds idle or five minutes total) or is evicted, refresh to continue; the Viewer will not silently mix pages from different snapshots. Exports use their own snapshot.

Table Viewer edits and deletes require index metadata access (`view_index_metadata` or equivalent) for the viewed target and the concrete index being changed. Rows can still be browsed without that privilege, but cannot be edited or deleted without a verified generation. Refresh after rebuilding an index with the same name.

The Viewer checks the index UUID before and after opening the read snapshot, then again immediately before each write. Elasticsearch still checks the document’s sequence number and primary term. The UUID checks are separate requests, not atomic: inconsistent cluster state during snapshot creation, or a rebuild after the final metadata check but before the server resolves the write target, can defeat them. Do not rebuild an index while editing it. REST previews copied into the Query Editor or another client are raw requests and do not include the Viewer’s UUID check.

### MongoDB

Table Viewer requests MongoDB cursor batches of eight documents. Schema sampling is limited to 2 MiB per BSON document and 4 MiB total. A grid page or table export chunk is limited to 2 MiB per BSON document and 8 MiB total (4 MiB per row and 16 MiB total for display text). Filters and sorts evaluated in RapiDB must scan the complete candidate set within 10,000 documents, 16 MiB of BSON and 24 MiB of display text, before the normal page limits apply. Each read also supports at most 1,024 distinct fields. If a limit is exceeded, RapiDB reports an error instead of dropping documents, exposing partial rows for editing, or publishing an incomplete export. A smaller page can help with page limits; for larger documents or failed schema samples, use a projected query or a database-native export.

MongoDB `find` and `aggregate` results also have a safety budget. The default sample is 100 documents; requesting more cannot bypass the 10,000-document ceiling, including with `find().limit(0)`. Negative and fractional chain limits are rejected; `aggregate().limit()` requires a positive integer. A probe document detects actual truncation without becoming part of the displayed schema. Exporting a truncated query result requires confirmation and exports only the displayed rows.

MongoDB `NumberInt(...)` and `NumberLong(...)` literals require one integer argument within the signed BSON int32/int64 range. Fractional, malformed, overflowing, and unsafe JavaScript number arguments are rejected before any operation in the script is sent. For exact large integers, use strings such as `NumberLong("9223372036854775807")` or bigint arguments rather than unquoted JavaScript numbers.

Bare JavaScript bigint values must also fit signed BSON int64, including nested fields and computed values. Overflow is rejected before the script starts instead of silently wrapping to a different stored value or row ID. Use `NumberDecimal("...")` or strings for larger exact values.

MongoDB `NumberDecimal(...)` requires exactly one string argument, such as `NumberDecimal("0.123456789012345678901")`. Numeric arguments are rejected before any operation in the script is sent because JavaScript can round them before Decimal128 conversion.

MongoDB `BinData(subtype, base64)` requires an integer subtype from 0 to 255 and a canonical base64 string (including padding when needed). Invalid literals are rejected before any operation in the script is sent, rather than silently decoding to different bytes.

MongoDB regular expressions preserve the `i`, `m`, `s`, and `u` flags in BSON. JavaScript-only flags `d`, `g`, `v`, and `y` are rejected before any operation in the script is sent; they must never be silently dropped or converted into different matching rules for an update or delete.

MongoDB `Date` / `ISODate` literals reject invalid dates before any operation in the script is sent. `ISODate` follows mongosh: it accepts no arguments (current time), one ISO-8601 date string (interpreted as UTC when no time zone is given; compact forms such as `20260101T000000Z` are accepted), or one Date value. `Date` keeps JavaScript's rules: it accepts no arguments, one date string or Date value, or one to seven safe integer arguments, and both strings without a time zone and calendar-component arguments follow JavaScript's `Date` constructor; use an ISO string with an explicit time zone for an unambiguous instant. Arguments are never silently discarded, and invalid dates cannot become Unix epoch during BSON serialization.

MongoDB updates and deletes require an explicit document filter; use `{}` explicitly to target all documents. Cursor modifiers on non-cursor operations, such as `deleteMany({}).limit(1)`, are rejected rather than silently ignored. Explicit database/collection names must be non-empty strings. BSON `Timestamp(t, i)` and `Timestamp({t, i})` components must be unsigned 32-bit integers, without coercion or rounding (`Timestamp(t)` defaults the increment to zero). Invalid filters, namespaces, modifiers, and timestamps are rejected before any operation in the script is sent.

MongoDB `insertOne`, `insertMany`, `updateOne`, `updateMany`, `deleteOne`, and `deleteMany` helpers do not support an additional options argument. Such calls are rejected before any operation in the script is sent: options such as `collation`, `upsert`, or `ordered` must never be silently ignored. Use `db.runCommand(...)` with explicit native command options when needed.

MongoDB validates supported helper names, cursor limits, find projection/sort shapes, aggregate pipeline arrays, and no-argument helpers before submitting any operation in a script. These helper validation errors cannot follow an earlier delete or insert. Scripts are still not transactions: database/SDK errors can follow successful operations.

MongoDB `createView` requires explicit non-empty view/source names and a pipeline array; use `[]` explicitly for an unfiltered view. Invalid pipelines are never replaced with an empty one, and options cannot override the named source or pipeline. Supported cursor modifiers are `limit`, `skip`, `toArray`, `pretty`, and `sort` for find helpers only. Other modifiers, including `explain`, `close`, and `collation`, are rejected rather than silently ignored; `toArray` and `pretty` accept no arguments.

### Redis

Redis query scripts are fully tokenized before the first command is sent. Invalid Unicode escapes and unpaired UTF-16 surrogates are rejected rather than addressing a replacement-character key or partially executing a script with a later parsing error. This validation does not make Redis scripts transactional; server-side errors can still follow successful commands.

Redis structured table edits (hash, list, set, sorted set) reject JSON numeric literals that would lose precision before any replacement is sent. Use quoted strings for exact large integers or decimal member values, such as `{"account":"9007199254740993"}`. Ordinary Redis string values are not interpreted as JSON.

## Results and exports

Truncated results show a warning. `rapidb.queryRowLimit` controls the number of displayed rows, subject to a hard ceiling of 10,000 rows; increasing the setting above 10,000 does not lift that ceiling. This display limit does not limit rows affected by a mutation or cancel query execution. Query-result exports include only the displayed rows; use JSON when preserving value types matters.

Query and table CSV exports use UTF-8 without a byte order mark (BOM) by default. Enable `rapidb.export.csvUtf8Bom` if Excel on Windows misreads non-ASCII text when opening a CSV directly. Leave it off for CSV readers that treat the BOM as part of the first column name.

Table exports keep a stable column schema across chunks. SQL NULL is written as `(NULL)` in both table and query-result CSV exports; empty strings stay empty. Missing fields are written as `MISSING`. Marker-like strings are not escaped. When a column contains both a marker and the same literal value, CSV export fails, even across chunks. CSV cannot distinguish an isolated marker from an identical literal: use JSON when retaining types or missing values matters. Spreadsheet formula-like strings are protected by an apostrophe prefix. A later unexpected column fails the export rather than silently dropping data. JSON applies the same unexpected-column check. Failed exports leave an existing destination file intact.

Exports are staged in the destination directory. For a new file, RapiDB probes hard-link support before loading table rows. If the probe succeeds, RapiDB tries to publish the completed staging file with a hard link. If the probe or final link fails with an error treated as lack of hard-link support (such as `ENOTSUP` or `EPERM`), RapiDB copies the completed staging file instead. Other probe failures stop the export before table rows are loaded; other final link failures do not fall back to copying.

Neither method overwrites a file that appears at the new destination. A successful hard link makes the complete file visible at once; an exclusive copy is not atomic, so readers may see partial content while it runs. A later filesystem or permission change can still make publication fail.

On POSIX, confirmed replacement of an existing file uses a single rename, subject to the filesystem's rename guarantees. On Windows, replacing an existing file is not supported: choose a new name. No portable compare-and-swap is available for an existing POSIX destination, so avoid changing that path concurrently. None of these methods guarantees durability after power loss.

MongoDB table and query JSON exports use canonical Extended JSON for BSON values. For example, a BSON Long uses `{"$numberLong":"9007199254740993"}`, so JSON readers do not round it to a JavaScript number. Deprecated BSON DBPointer values in table rows, query documents, and command replies use `$dbPointer`; ordinary DBRefs keep `$ref` and `$id`. JSON export stops if the driver cannot distinguish an exported DBRef from a DBPointer, or if a literal document contains reserved Extended JSON keys such as `$oid`. Use a BSON backup if you need to preserve such data. CSV is unchanged: query CSV uses display values, and MongoDB table CSV still renders DBPointer as DBRef.

When editing a MongoDB DBRef in Table Viewer, use `"$id":{"$oid":"507f1f77bcf86cd799439011"}` for an ObjectId or `"$id":{"$string":"507f1f77bcf86cd799439011"}` for a string with the same spelling. The `$string` marker is only for the table editor; it does not appear in exports. Older DBRef drafts with an ambiguous ID are not applied automatically. Refresh and re-enter the edit with the intended type.

## Table editing

Persisted edits are prevalidated against available column metadata before any write. Known unsupported edits fail before the batch is applied; where representation compatibility depends on the stored value, verification runs in the transaction and a mismatch rolls it back. Preview skipping does not bypass validation or verification. Schemaless sampling is not a complete database schema or a guarantee that every value has the sampled type.

SQL table updates must affect exactly one row per edited row; an unexpected count aborts the transaction. This also protects against a cached primary key becoming non-unique after an external schema change. Table updates require rollback support, including temporal-only updates on MySQL; nontransactional engines such as MyISAM are blocked. Oracle catalog lookups preserve the exact identifier spelling, so quoted mixed-case objects do not borrow metadata from uppercase namesakes.

SQL table deletes also require rollback support, even when the selected rows fit into one DELETE statement. Storage-engine support is checked again after preview confirmation and before execution, so a stale selection or changed engine cannot bypass this safeguard.

For MySQL and MariaDB, rollback-dependent Table Viewer writes (updates, deletes, verified inserts, and a batch Apply) hold metadata locks on the target tables from the safety check through transaction completion. They are blocked if a relevant trigger exists or the connection cannot prove it has permission to see all relevant triggers. A transaction-capable engine does not make trigger side effects rollback-safe. Visibility is proven by a `TRIGGER` (or `ALL PRIVILEGES`) grant at the global level, on the exact table, or on the database. Privileges of active roles count: MySQL 8 grants are read with `SHOW GRANTS FOR CURRENT_USER() USING` the roles from `CURRENT_ROLE()`; for MariaDB the current role and the roles granted to it are listed too. A database-level grant counts when it names the database exactly — including an escaped literal such as `` `my\_app`.* `` or an unescaped `` `my_app`.* `` — and every database-level grant that could match the name (as a pattern, as a literal with `partial_revokes`, or in another letter case) includes `TRIGGER`, because the server applies only the first matching row. Pure wildcard grants such as `` `sales%`.* `` are not proof. If visibility still cannot be proven, nothing is written and RapiDB asks for an explicit confirmation: **Apply Without Trigger Check** retries that one change with only those tables exempt from the grant proof. Triggers that are visible still block the write, but a hidden trigger may have side effects that a rollback does not undo — the rollback guarantee does not cover them. Declining (or any environment without the prompt) keeps the write refused. The guard does not serialize concurrent grant administration. A standalone insert that does not require verification remains a single statement without this rollback guarantee.

MongoDB Table Viewer can edit and delete existing documents only on a verified standalone server or non-sharded replica set. It does not route by shard key, so these actions and their previews are disabled on `mongos` (including unsharded collections behind it), load-balanced endpoints, direct shard/config servers, and when topology cannot be verified. On replica sets of every MongoDB version, verification runs `$collStats` on the collection (a shard member reports its shard name there) and requires the `collStats` privilege; standalone servers are not probed. Browsing, export, and inserts remain available subject to connection permissions. To edit or delete a document in a sharded collection, use the Query Editor with the full document key (including the shard key).

SQLite Table Viewers for attached databases are bound to the attachment they originally read. You can still run `ATTACH` and `DETACH` in the Query Editor. If you detach a viewer's alias, even if you reattach the same file or reuse an in-memory alias, close and reopen the viewer to work with the new attachment. Refresh does not switch targets or transfer pending edits or previews. Drafts for attached databases and SQLite's `temp` schema are not restored across extension restarts because the original attachment cannot be verified.

Temporal-value verification is driver-specific: SQL Server and Oracle verify explicitly edited dates/times, while PostgreSQL, MySQL, and SQLite retain their existing temporal verification exceptions. Exact temporal persistence is not guaranteed by this safeguard for those three drivers.

MySQL `TINYINT(1)` is not restricted to boolean storage. Values outside `0`/`1` are preserved in query results, table reads, row keys, and exports rather than converted to booleans.

MySQL spatial table reads and exports retain nonzero reference systems as `SRID=4326;POINT(1 2)`. Editing with plain WKT preserves the existing SRID; use an explicit `SRID=...;` prefix to change it. New plain-WKT values default to SRID 0. Optimistic update checks compare both the SRID and coordinates.
